# 南航上海路小站微信小程序开发规则

## 项目定位

本项目是“南航上海路小站”微信原生小程序。

产品定位：

* 仅服务南昌航空大学上海路校区
* 年轻校园生活小站
* 核心模块包括：

  * 饭点帮拿
  * 校园墙
  * 集市与求购墙
  * 服务榜
  * 我的

技术约束：

* 微信原生小程序
* JavaScript
* WXML
* WXSS
* 不使用云开发
* 不使用 npm
* 不使用 TypeScript
* 不引入第三方 UI 库
* 接口地址从 `utils/config.js` 读取

## 视觉方向

页面风格必须保持：

* 年轻校园感
* 奶白色或浅米色背景
* 大圆角卡片
* 清爽、有活力
* 轻信息流
* 适当小标签
* 不做后台管理风
* 不做政务风
* 不做学校官网风
* 不做商务 SaaS 风
* 不大面积使用深绿色
* 不为了“高级感”过度增加动画和装饰

修改页面时应保持首页、帮拿、校园墙、集市和服务榜的视觉一致性。

## 总体工作方式

1. 每次任务开始前执行 `git status`。
2. 如果工作区不干净，先报告已有改动，不得直接覆盖。
3. 一次只完成一个明确小目标。
4. 修改前列出允许修改的文件白名单。
5. 白名单外文件不得修改。
6. 如果必须改白名单外文件，停止并向用户说明原因。
7. 不得顺手改其他页面。
8. 不得因为新增一个入口而重做首页布局。
9. 完成后执行 `git diff --name-only`。
10. 未经实际检查不得声称页面正常。

## 禁止操作

除非用户明确授权，否则禁止：

* push
* force push
* 上传微信小程序
* 发布体验版
* 修改 AppID
* 删除稳定页面
* 修改后端业务代码
* 清空数据库
* 引入云开发
* 引入 npm
* 引入 TypeScript
* 引入第三方 UI 库
* 添加支付
* 添加微信登录
* 添加 openid
* 自动 commit
* 修改真实联系方式
* 提交私有开发配置

## 稳定模块保护

以下模块已经形成稳定版本，修改其他功能时不得触碰：

* `pages/help/*`
* `pages/wall/*`
* `pages/market/*`
* `pages/service/*`
* `pages/index/*`
* `pages/mine/*`

只有任务明确列入白名单时才能修改。

不得因为修复求购墙而修改校园墙。
不得因为开发服务榜而修改帮拿。
不得因为新增入口而大改首页。

## WXML 强制检查

每次修改任何 `.wxml` 文件后，必须检查：

* 是否出现 `�`
* 是否出现 `?/view>`
* 是否出现破损的 `</view>`
* `{{` 与 `}}` 是否配对
* `placeholder` 引号是否闭合
* `bindtap` 引号是否闭合
* `wx:if` 表达式是否完整
* 标签是否正确嵌套
* 中文是否乱码
* 是否有未闭合的 input、textarea 或 view 属性

不得只运行 JavaScript 语法检查后就宣布页面正常。

## JavaScript 规则

1. 请求地址必须从 `utils/config.js` 读取。
2. 不得在页面中重复写死 BASE_URL。
3. 接口失败时使用 `console.error` 输出关键错误。
4. 不保留大量普通 `console.log`。
5. 接口字段名必须与后端真实 JSON 完全一致。
6. 页面跳转必须确认 app.json 已注册目标页面。
7. 详情页必须检查 options.id。
8. 发布成功返回列表后必须处理刷新逻辑。
9. 不得因热更新缓存异常直接修改业务代码。

## 常见错误处理

出现 `ERR_CONNECTION_REFUSED` 时：

1. 先检查后端是否运行。
2. 检查 8080 端口是否监听。
3. 不得先修改 WXML 或接口代码。

出现 `appid missing`、插件、缓存或证书错误时：

1. 先检查 project.config.json。
2. 重新打开或重新导入项目。
3. 清除开发者工具缓存。
4. 不得盲目修改业务页面。

出现 WXML 编译错误时：

1. 根据报错文件和行号修复。
2. 检查破损标签、引号和表达式。
3. 不得误判为后端错误。

出现接口 404 时检查请求路径。
出现接口 500 时查看后端错误栈。
出现页面空数据时检查接口是否返回、筛选条件和字段映射。

## 配置规则

1. `project.private.config.json` 不得提交。
2. `utils/config.js` 当前本地开发地址为：
   `http://127.0.0.1:8080`
3. 正式上线前才能切换 HTTPS 域名。
4. 不得擅自修改 AppID。
5. 不得把真实手机号、微信号、密码或 Token 写入代码。
6. 示例联系方式使用非真实占位内容。

## 测试规则

修改页面后至少完成：

1. app.json 可正常解析。
2. 修改的 JS 文件通过语法检查。
3. 修改的 WXML 通过破损扫描。
4. 页面路径和跳转路径存在。
5. 请求字段与后端接口一致。
6. 不影响其他稳定模块。

涉及核心流程时，必须验证：

* 列表加载
* 分类筛选
* 发布
* 详情
* 状态变更
* 返回刷新
* 空状态
* 请求失败状态

Codex 自动检查不能代替用户视觉验收。
最终页面效果必须由用户在微信开发者工具中确认。

## Git 规则

1. 任务前执行 `git status`。
2. 任务后执行：

   * `git status`
   * `git diff --name-only`
3. 不提交：

   * project.private.config.json
   * 日志
   * 缓存
   * 截图
   * 临时文件
   * 真实联系方式
4. 只有用户明确要求封版才 commit。
5. commit 前列出文件。
6. commit 后报告 commit id。
7. 永远不自动 push或上传小程序。

## 用户介入范围

用户只负责：

* 输入密码
* 确认危险操作
* 确认是否删除或重建数据
* 登录微信开发者工具
* 页面视觉验收
* 正式上传、部署、push 等最终授权

其他可以自动完成的检查、编译、接口测试和 Git 检查，由 Codex 自己执行。

## 完成报告格式

每次任务结束必须报告：

1. 本轮目标
2. 修改文件
3. 白名单外文件是否有变化
4. 自动检查内容
5. 接口测试结果
6. WXML 检查结果
7. Git 状态
8. 遗留问题
9. 需要用户视觉验收的页面

不得只说“已完成”或“没有问题”。

创建完成后：

1. 显示 AGENTS.md 路径。
2. 检查内容完整性。
3. 执行 git status。
4. 不 commit，等待用户确认。

# 项目经理与主动规划规则

## Codex 的角色

Codex不只是代码执行工具，同时承担本项目的技术负责人和迭代协调角色。

Codex需要：

1. 理解当前项目的产品定位。
2. 了解当前已完成功能。
3. 判断本轮任务是否值得做。
4. 主动指出需求中的范围过大、顺序错误或风险。
5. 每轮完成后主动提出唯一的下一步建议。
6. 不得无条件顺从用户提出的每个功能。
7. 如果用户的方案会扩大风险、破坏稳定版本或偏离核心目标，应直接说明。

## 产品核心定位

“南航上海路小站”只服务南昌航空大学上海路校区。

产品不是普通二手平台，也不是功能堆砌型校园 App。

当前核心定位：

* 饭点帮拿：最高频、最经过验证的核心入口
* 校园墙：承接失物招领、新生提问、校园动态
* 集市与求购墙：解决闲置交易和二手冷启动
* 服务榜：后续商业化与校区生活服务入口
* 我的：个人任务和发布内容管理

当前不应优先开发：

* 表白墙
* 树洞
* 复杂社交
* 评论系统
* 点赞系统
* 在线聊天
* 平台支付
* 复杂商家后台
* 无明确需求的大型功能

## 当前稳定版本

当前已经完成：

* V0.4 饭点帮拿
* V0.5 校园墙基础版
* V0.6 求购墙
* V0.7 服务榜小程序化

当前已有页面包括：

* 首页
* 帮拿列表、发布、详情、我的帮拿
* 校园墙列表、发布、详情
* 集市与求购墙
* 发布求购、求购详情、我的求购
* 服务榜列表、服务详情
* 我的页

当前阶段已经形成可以演示的 MVP。

## 当前优先方向

接下来优先级按以下顺序判断：

1. 当前版本稳定性和回归验收
2. README、项目文档和演示材料
3. 真实用户体验测试
4. 修复真实测试中发现的问题
5. 体验版与上线准备
6. 微信登录、身份体系和内容审核
7. 图片上传
8. 真实商家和服务榜运营数据
9. 新功能扩展

不得因为用户说“继续”，就默认开发新功能。

如果当前版本尚未验收、工作区不干净、存在未解决错误或未提交改动，应优先收敛当前版本。

## 下一步判断规则

每轮任务完成后，Codex必须结合以下信息判断下一步：

1. 当前 Git 状态是否干净。
2. 本轮功能是否已自动测试。
3. 是否仍需要用户视觉验收。
4. 是否存在阻塞错误。
5. 当前版本是否已 commit。
6. 下一步是否直接服务于核心产品目标。
7. 下一步是否会扩大系统复杂度。
8. 是否存在更低成本、更高价值的替代方案。

下一步建议必须只给一个主建议，不要一次给多个并列开发方向。

建议格式：

## 建议的下一步

任务名称：

为什么现在做：

预期价值：

预计涉及模块：

风险：

需要用户确认的事项：

在用户确认前，不得自动执行下一步。

## “继续”的处理规则

当用户只说“继续”“下一步”或类似表达时：

1. 先读取 AGENTS.md。
2. 执行 git status。
3. 查看最近提交和当前未提交变化。
4. 结合当前稳定版本判断项目所处阶段。
5. 主动提出一个最合理的下一步。
6. 不得立即改代码。
7. 等用户确认后再执行。

## 需求评审规则

用户提出功能时，先判断：

* 是否解决真实需求
* 是否符合上海路校区场景
* 是否属于当前阶段
* 是否已有类似功能
* 是否会影响稳定模块
* 是否有更简单的实现方式
* 是否需要后端配合
* 是否有内容安全或运营风险

如果不值得现在做，应明确反对并解释原因。

## 每轮结束报告补充

除原有完成报告外，每轮结束必须增加：

1. 当前项目所处版本。
2. 当前版本是否可以封版。
3. 当前最主要的风险。
4. 建议的唯一下一步。
5. 下一步是否需要用户视觉验收或关键授权。
